# GUI/headless parity matrix

**Status:** 2.0 M0 (spec-2.0 §5.3), written against `release/2.0` at `9b00985` (host 1.4.0,
Houdini 22.0.466). Every row was found by reading the code (citations are `file:line` under
`src/hocuspocus/` unless a path says otherwise); the rows marked *probed* were also checked in
a scripted `houdinifx` session with an isolated pref dir. 2.0 M3 closed the gaps below as
the Status column says (the matrix rows are updated to match). 2.1 removed `compat_1x`
(BIBLE D46): rows that named a 1.4 tool (`viewport_capture`, `selection`,
`node_type_info`, `problems`, `usd_stage`) name its 2.0 form. The GUI column is executed by
`tests/integration/test_parity_gui.py` (markers `slow` and `gui`, deselected unless `--rungui`):

```bash
.venv/Scripts/python -m pytest tests/integration/test_parity_gui.py --rungui -q
```

It runs in the dev venv's Python (no hython), launches `houdinifx` through
`bridge/launch.py` with an isolated `HOUDINI_USER_PREF_DIR` (the dev package JSON and a
`profile = "full"` toml), an isolated `HOCUSPOCUS_STATE_DIR` and port 0, drives the host over
`POST /hp/v1/call`, and closes Houdini with `houdini_connect {quit}`. About 30 s on the 1.4
release machine. The headless column is the ordinary integration tier.

Legend:

- **same**: identical behaviour and result shape in both.
- **mode**: a deliberate, documented difference (BIBLE, `notes`, or a tool's own result).
- **gap**: a difference that is undocumented, surprising to an agent, or risky. Each gap is
  listed below with a proposed 2.0 resolution: make it a **mode** (document it and say so in
  the result) or make it the **same**.

### Modal dialogs in a GUI session (G5): text for the guide

The guide recipe "GUI sessions: never open a dialog" (`bridge/instructions.py`) carries
this, tightened:

> **Never open a dialog in a GUI Houdini.** A modal `hou.ui` call (`displayMessage`,
> `selectFile`, `readInput`, `selectNode`, ...) made from `houdini_python`, a parm
> callback run by `parm_set {press}` or an `edit` `set` op with `press`, or an asset's
> creation script fails the call with `ui_required` naming it, and the call is rolled
> back; headless the same code raises an `AttributeError` (there is no `hou.ui`). A hip
> file's load script that asks for a dialog is stopped there, and `hip_open` reports it in
> `warnings`; the file is loaded. Pass values as arguments instead of asking for them,
> write messages to stdout (they come back in the result), and press a button only when
> you know its callback opens no dialog. A dialog the *user* has open still holds
> Houdini's main thread: nothing HocusPocus sends runs until it is closed, and calls
> return `houdini_busy` with `detail.started: false`. When calls keep doing so and
> `houdini_status` shows `busy: true` with no job running, ask the user to look at
> Houdini for an open dialog.

Not gaps, but worth knowing: review 19's "`hip_save` in the GUI emits `ParmTupleChanged`
on a ROP" was not reproduced with a Geometry ROP in the probe session (only `AfterSave`
was recorded).
